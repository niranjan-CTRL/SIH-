# H2S Sentinel — Software Prototype

Team Valence · SIH 2026 · Problem Statement SIH26118

This is the **software layer** of the H2S Sentinel project: worker + supervisor
web dashboards, a backend API, a database, and an AI cartridge-color-analysis
pipeline. It does **not** include the physical smartwatch hardware (ESP32,
MAX30102, MPU6050, chemical cartridge) described in the project spec — that
needs real components and lab calibration, which can't be built or validated
in a software sandbox. Wherever the software stands in for a hardware signal
(e.g. live H2S readings), it's clearly labeled as simulated.

## What's real vs. simulated

| Piece | Status |
|---|---|
| Login, shift lifecycle, database | Real, fully working |
| H2S/HR/SpO2 threshold & alert logic | Real, fully working |
| Cartridge photo → color extraction (OpenCV) | Real, fully working |
| Color → exposure-dose regression model | Real pipeline, **trained on synthetic data** (see below) |
| Live sensor readings on the worker dashboard | **Simulated** in the browser — swap for real ESP32 BLE/Wi-Fi data by POSTing to the same `/api/sensors/{shift_id}/reading` endpoint |
| ESP32 firmware, wearable hardware | Not built — out of scope for a software sandbox |

### About the AI model

The project spec is explicit: *"Actual values MUST come from controlled
experiments; never invent results."* Since no real calibration data exists
yet, `backend/app/ai/generate_synthetic_calibration.py` generates a clearly
labeled **synthetic** dataset so the pipeline has something real to train
and run on. Every prediction the API returns carries
`is_validated_model: false` and a disclaimer. To go live for real safety use:
run the lab calibration protocol in spec section 23/29, replace
`calibration_data.csv` with the real data, and re-run `train_model.py` — no
other code changes needed.

## Architecture

```
frontend (React + Vite)  →  backend (FastAPI)  →  SQLite/Postgres
                                    │
                                    └→ AI pipeline (OpenCV + scikit-learn)
```

## Running locally

**Backend**
```bash
cd backend
pip install -r requirements.txt
python -m app.ai.generate_synthetic_calibration   # one-time: builds demo dataset
python -m app.ai.train_model                       # one-time: trains placeholder model
uvicorn app.main:app --reload --port 8000
```
API docs at `http://localhost:8000/docs`.

**Frontend**
```bash
cd frontend
npm install
echo "VITE_API_URL=http://localhost:8000" > .env
npm run dev
```
Open `http://localhost:5173`.

Demo accounts (seeded automatically): worker `W101` / PIN `1234`,
supervisor `S001` / PIN `9999`. Demo cartridges: `H2S-CART-001`, `H2S-CART-002`.

## Deploying (why I can't do this last step for you)

I built and tested this fully in my sandbox, but my sandbox's network access
is restricted to package registries (PyPI/npm) and GitHub — it can't reach
Vercel, Render, Railway, etc., and I don't have your cloud accounts. Here is
the fastest real path to a public URL, using free tiers:

### 1. Backend → Render
1. Push this repo to GitHub (see below).
2. On [render.com](https://render.com): New → Web Service → connect the repo,
   root directory `backend`. Render will detect `render.yaml` and the
   `Dockerfile` automatically.
3. Deploy. Note the resulting URL, e.g. `https://h2s-sentinel-backend.onrender.com`.

### 2. Frontend → Vercel
1. On [vercel.com](https://vercel.com): New Project → import the same repo,
   root directory `frontend`.
2. Set environment variable `VITE_API_URL` = your Render backend URL from step 1.
3. Deploy. Note the resulting URL, e.g. `https://h2s-sentinel.vercel.app`.

### 3. Close the loop
Go back to Render → your backend service → environment variables → set
`FRONTEND_URL` to your Vercel URL (tightens CORS from `*` to just your app),
then redeploy the backend.

That's it — two dashboard clicks and one env var round-trip, all pushed via
the platforms' free tiers.

## API reference

Full interactive docs are auto-generated by FastAPI at `/docs` once running.
Key endpoints:

- `POST /api/auth/login`
- `POST /api/shifts/start`, `POST /api/shifts/{id}/end`
- `POST /api/sensors/{shift_id}/reading`, `GET /api/sensors/{shift_id}/latest`
- `POST /api/cartridge/scan` (multipart image upload → AI analysis)
- `POST /api/alerts/sos`
- `GET /api/supervisor/workers`, `GET /api/supervisor/alerts`
- `GET /api/reports/{shift_id}`

## Environment variables

See `backend/.env.example`. Never commit real secrets — `JWT_SECRET` should
be a long random string in production, generated by Render/Railway automatically
if you use the provided `render.yaml`.
